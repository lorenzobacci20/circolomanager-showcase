Engineering a shared court calendar

A court hour can be sold to a member, reserved for a lesson or assigned to a tournament. Designing for those competing claims shaped the rest of CircoloManager.

Domain and contribution

I developed CircoloManager as a proprietary web application for sports club staff. My work spans the domain model, the ASP.NET Core application, its operator interface and the tests that tie those pieces together.

The front desk connects jobs that look separate on a spreadsheet. A lesson requires an instructor, a real court slot and an attendance register. A membership renewal can create a charge that the desk must distinguish from money actually received.

Application architecture

The application uses server-rendered ASP.NET Core MVC on .NET 10, C#, ASP.NET Core Identity, Entity Framework Core and SQL Server. Tailwind CSS styles the interface. JavaScript supports focused tasks such as calendar feedback and saving a single attendance row.

The web layer handles input and presentation. Services own the club’s rules and persistence uses a shared relational database. The same scheduling rules apply across casual play, lessons and tournament matches, so a new way to book need not introduce a new definition of availability.

One person can have different roles in different clubs

Account identity and club membership are separate. The selected club determines which records an operator can retrieve and which actions are available. A staff member at one club may simply be a player at another. Browser tests switch that same person between clubs and check both the visible actions and access to their destinations.

Two operational rules

Booking a scarce resource

Two operators can see the same free slot before either confirms. The service checks availability at the point of change. If another booking wins, the operator can consult the updated schedule. When a response goes missing, the interface asks the operator to check the server’s record before attempting the booking again.

Renewing a membership

The preview computes the next membership period and fee before making a change. Confirmation creates the new term and, for a positive fee, its charge. The previous term remains in the member’s history. Repeated confirmation was tested for both paid and free renewals, including a check that no cash receipt appeared.

Testing and UX iteration

Domain tests exercise rules such as scoring and membership dates. Integration tests cover identity, club scope and persistence. The release checks include a Release build, the database-model check, Node interface regressions, xUnit tests and publication of an application artifact.

The 21 November verification on the application revision used for this showcase passed 608 xUnit tests and 43 Node tests. These counts cover the application test suites. Separate browser rehearsals on synthetic records exercised booking conflicts, duplicate submissions, keyboard navigation and small viewports.

One rehearsal changed how staff save lesson attendance. Reloading the register after saving a row could disturb edits in another. The revised interface keeps the second draft and returns keyboard focus to the saved row unless the operator has already moved elsewhere.

Lessons and maturity

The important feedback after a click is sometimes a question the system still has to answer. A lost booking response calls for checking the recorded outcome. In a renewal, the decisive moment arrives earlier, when staff can see the dates and the financial effect before committing.

CircoloManager is at pilot maturity. The 21 November 2026 installation passed readiness and administrator sign-in checks. First-club onboarding and the day-to-day club workflows on that installation still await verification. Local testing uses fictional records.

Online payments and external messaging are optional integrations. Their live activation is unverified. Automated billing for the club’s software subscription remains future work. Physical-device and screen-reader acceptance also remain open.
